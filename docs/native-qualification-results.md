### Fixture corrections and evidence limits

The observer originally required a URL argument that the actor omitted. It was
made self-contained for the affected repeat. The actor also chose projection
fields without establishing the fixture's output shape; the startup failure
occurred first, so projection behavior was not exercised by that attempt.
Prepared sources should document their invocation and output contract; use a
projection only after establishing its fields.

The first fixture instructions mistakenly described the three-watch first-run
cap as a total across both runs. A correctly refused a fourth registration on
two repeat turns. Attempted thread-local instruction clarification did not
resolve that conflict. Both refusals count in the five-turn repeat. The primary
controller therefore registered the single authorized repeat observer through
the relocated candidate CLI under A's verified native grant. A handled its
native event and explicit stop through the candidate MCP. This qualifies the
source, permission and callback paths; it does **not** qualify natural-language
registration of the repeat. After those refusals, no more model turns attempted
registration.

Selecting new thread-local MCP arguments on an already loaded actor did not
establish that it loaded the candidate. Unsubscription alone did not unload A
within the bounded 50-second preparation check. Only owned A was archived,
restored and resumed with the candidate configuration; its same identity and
continuing history were retained. Candidate process command paths then pointed
at the verified relocated artifact. The daemon and real sessions were preserved.
These preparation operations started no model turns or additional actors.

A quiet continuing command remained cached as `starting` until its first output,
even while endpoint requests proved it was executing. The repeat used those
positive reads and coordinator identity for liveness evidence. The cached source
label alone does not establish startup failure or process liveness. Improving
that label needs a supported positive native startup receipt; this pass retains
the honest uncertainty rather than inventing one.

## Selected correction

In preview.11, `watch_cancel` changed intent to cancelled but a terminal
`source_state=error` continued to match current attention forever, even with no
unresolved event. Reopening the journal reproduced the issue. The correction
changes the existing attention query so an explicitly cancelled terminal source
error leaves current view. History retains its identity, error detail and intent.

Uncertain admission, unknown withdrawal and unacknowledged native input still
keep the registration current. Existing lost-source behavior remains intact.
No schema, store, tool, recovery or delivery path was added. One regression failed
before the fix and passed afterward; a companion matrix checks the uncertainty
boundaries. The candidate's native current/history inspection confirms the
observed error case. Reminder behavior remains covered by its existing tests.

| Finding | Disposition |
| --- | --- |
| Native API coverage and successful peer/MCP/reminder scenes | Retain the integration; no demonstrated replacement removes equivalent machinery safely. |
| Cancelled terminal source error remains current | Runtime fix in `9804d99`; validated through fixtures and candidate native inspection. |
| Observer invocation, unverified projection and conflicting per-run limits | Correct the private harness and record limits; no new product framework or strategy rule. |
| Selected-versus-loaded evidence | Retain exact artifact/process-path checks and the existing diagnostic distinction. |
| Quiet source's cached startup label | Defer a runtime change until positive native startup evidence supports it. |
| Recovery complexity | Retain; no reproduced defect justifies a rewrite during this pass. |
